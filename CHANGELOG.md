## [Unreleased]

### Breaking changes

- Renamed the public facades to neutral names ahead of the web targets:
  `JvmEditableParagraphFacade` → `EditableParagraphFacade`,
  `JvmEditableLineFacade` → `EditableLineFacade`,
  `JvmFlowCompositionFacade` → `FlowCompositionFacade`,
  `JvmIncrementalParagraphLayoutSession` → `IncrementalParagraphLayoutSession`,
  `JvmEditableLineLayoutSession` → `EditableLineLayoutSession`, and their
  `*Request` companion types. No deprecated aliases are provided.
- `EditableLineFacadeRequest` and `EditableParagraphFacadeRequest` expose a single
  constructor each. The historical and "source- and binary-compatible" overloads are
  removed — an unpublished incubating library has no compiled consumer to protect, and
  three constructors per request invited a caller to take a route that silently chose an
  unbounded operation profile. `positioning` and `operationProfile` now default exactly as
  those routes behaved, so a caller that never named them is unaffected, and the Java-only
  `LegacyEditableLineFacadeRequestFactory` test helper is gone with them. No deprecated
  aliases are provided.

### Added
- The web targets are verified with the same authority as the JVM, Android and iOS ones. `:kalligraphie:e2e` gains `js` and `wasmJs` targets whose corpus is embedded exactly as the iOS simulator binary's is (`webFixtureCorpus`), and the two shared tests that render the whole catalogue now await the portable `initialize()`: the shared harness is synchronous and the WebAssembly HarfBuzz module is instantiated asynchronously, so a shared `initializedSceneTest` runs them on a test scope that waits for the real promise. The web suites of `:kalligraphie`, `:kalligraphie:shaping` and `:kalligraphie:platform:browser` also run in **Chrome headless** through Karma, so the artifacts are proven in a real bundler and the Local Font Access adapter against an actual `window`; its browser test asserts that the typed outcome tracks whether `window.queryLocalFonts` exists rather than a fixed result, since Node answers `Unsupported` while Chrome implements the API. Two publishing defects in `:kalligraphie:platform:browser` were forced out before the release, both invisible until an artifact was actually published: its `webMain` seam named JavaScript types (`Promise`, `kotlinx.coroutines.await`), which the intermediate `web` metadata compilation cannot resolve, so the module could not be published at all — the seam now speaks only Kotlin and each target awaits the browser promise and copies the `Blob` itself — and it published as `org.graphiks:browser` instead of joining the `kalligraphie-platform-*` coordinate family of the other platform adapters. Merging master's WOFF 1.0/2.0 container support into the web targets then forced the last piece: the WOFF 1.0 reader inflated its tables through Okio's `InflaterSource`, which exists on the JVM and native targets alone, so it now routes through the same portable decompression seam the PNG and SVG-in-OT decoders use, and the decoders' allocation boundary moves behind a portable `ContainerAllocationError` actual instead of naming `OutOfMemoryError`. The WOFF round-trip tests build their fixtures with a small portable zlib encoder in the test sources instead of Okio's `Deflater`, so they run on every target — including `js` and `wasmJs` — and the encoder is validated against Okio's own inflater on the JVM and the portable one on web; the web target also decodes the real `woff-ibm-plex` fixtures through the container scenes and the container robustness probes.
- `Kalligraphie.embedded` and the byte-backed JVM directory capture accept WOFF 1.0 and WOFF 2.0 single-face containers in addition to the containers they already accept — standalone SFNT for the embedded facade, and standalone SFNT plus TTC/OTC collections for directory capture: an internal `FontContainerDecoder` sniffs the `wOFF`/`wOF2` signature and reconstructs a standalone SFNT that the existing `SfntReader` path consumes unchanged, so layout, metrics, outlines, colour and bitmap routes behave exactly as for the unwrapped font. The WOFF 2.0 reader decompresses the single Brotli font-data stream through the portable bounded Brotli decoder and reverses the `glyf`, `loca` and `hmtx` transforms; the WOFF 1.0 reader inflates each table's zlib stream. Decoding is `commonMain` only and bounded by a `WoffDecodeLimits` whose limits are independent of the untrusted declared lengths, so a malformed, hostile or oversized container is refused before any unbounded allocation with stable typed codes (`font.woff.invalid-header`, `font.woff.invalid-table-directory`, `font.woff.invalid-deflate`, `font.woff2.invalid-header`, `font.woff2.invalid-table-directory`, `font.woff2.unknown-transform`, `font.woff2.brotli-failed`, `font.woff2.invalid-font-data-size`, `font.woff2.transform-failed`, `font.unsupported-container`, `font.resource-limit-exceeded`); WOFF/WOFF2 collections (`flavor == 'ttcf'`) stay refused as unsupported containers. Face identity is decoded-byte identity, not container identity: `FontFaceId.source` for a WOFF/WOFF2 input is the content digest of the reconstructed SFNT, so two encodings of one font generally do not share identity (WOFF 2.0 reconstructs `glyf`/`loca` in a permitted, non-byte-identical form) and capture deduplicates by the decoded digest. The corpus gains `woff-ibm-plex` (the same OFL IBM Plex Sans Regular text font as both `.woff` and `.woff2`, decoding to different bytes), `:kalligraphie:e2e` promotes `container.woff` and `container.woff2` to supported golden scenes with a semantic cross-container equivalence test. The non-published `:kalligraphie:bench` module measures WOFF and WOFF2 container capture and end-to-end glyph resolution on every platform.
- `:kalligraphie:e2e` proves **real letters with variable colour**: the corpus gains **Kalnia Glaze**, a real OFL variable COLR v1 Latin font (`wght` 100–700, `wdth` 100–125, a nine-colour first palette, no SVG table), and the catalogued scene `sheet.paint.kalniaglaze-latin.48` renders its A–Z capitals at `wght` 100 and 700, asserting per-cell ink, chroma and a visible variation between the two weights. The COLR v1 profile now accepts `Group` paint graphs, which the real font's `PaintColrLayers` roots need. The corpus checks (`fetch_fonts.py --check --provenance`, the fixture-tree coverage tests and the exhaustiveness lint) cover the new family.
- `:kalligraphie:raster-cpu` composes the COLR v1 variable paint surface: `GlyphClip`, `Solid`, `LinearGradient` and `Transform` join `SolidOutline`, `Path` and `Group`. Clipping intersects coverage exactly at the sixteen fixed sub-pixel samples so a shared edge is never squared, an unbounded paint is bounded by the clips enclosing it, and gradients are shaded in a committed integer sRGB transfer so no platform math can move a byte; `PathClip`, `RadialGradient`, `SweepGradient`, `Composite`, a clip around a `Group`, and gradients that are not `LINEAR_SRGB` + `PREMULTIPLIED` stay typed refusals. `:kalligraphie:e2e` promotes `color.colr-v1-variable` to a supported golden scene (`sheet.paint.kalligraphie-var-colr.64`) that renders the variable fixture at two design weights and asserts each raw raster differs, and its `glyf`/`loca` tables are now claimed instead of excused.
- Per-span paragraph styling in the JVM reference paragraph route. `ParagraphStyleSnapshot` carries an ordered, non-overlapping `ParagraphStyleSpan(range, face?, variation?)` list over one text version — `styleAt(index)` answers the covering span or `null` in a gap — and `ParagraphLayoutRequest` and `EditableParagraphFacadeRequest` gain an optional `styleSpans` field that defaults to `null`, so existing callers and the historical JVM constructors are unchanged. A span's `face` is a preference resolved the way Skia resolves one: for each fallback unit the preferred face (which must be a `resolutionPolicy.candidates` member) is tried first, then the policy order, and `lastResortFace` is never promoted. A span's `variation` is a design-axis selection: `null` inherits `fontInstanceDescriptor.variation`, `FontVariationCoordinates.default` resets the selected face to its own default instance (distinct from `null`), and a non-empty selection is strict on the primary candidate — every requested axis must be declared by the face or the candidate is rejected — but tolerant on fallback candidates, which drop the axes they do not declare and carry the new `font.fallback.span-variation-projected` WARNING; a preferred face that cannot shape a unit and falls through to a later candidate carries the new `font.fallback.span-face-unavailable` WARNING. `LayoutContinuation` captures and compares `styleSpans`, so resuming with different spans is rejected as incompatible instead of reusing the published prefix. **v1 boundary:** a span changes only the face and variation applied to the selected run — font size, OpenType features, paint and materialization stay paragraph-wide — the flow routes reject a request whose `styleSpans` is non-null before any region query or state reuse: the line-level flow route returns a `FlowCompositionError.ParagraphFailure` carrying a `ParagraphLayoutError.InvalidInput`, and the incremental flow route returns a `FlowCompositionError.IncompatibleState`; the standalone editable-line facade composes a single instance and has no span input, and per-span size, features and paint are deferred to an additive phase. `ParagraphConstraints.lineMetrics` still fixes the line-box rhythm and is not resized per span, though a line's content envelope follows each run's instance.
- The non-published `:kalligraphie:bench` module measures the paragraph profiles on every platform, now that `:kalligraphie:conformance` declares `END_TO_END_LAYOUT` present everywhere and the text facades and the portable Unicode analysis are `commonMain` code: the JVM and the Android device runtime run all forty-two profiles, and the iOS simulator runs forty-one. The eighteen paragraph scenarios move from `jvmMain` to `commonMain` unchanged, and the `expect/actual paragraphScenarios` seam whose only purpose was "the JVM alone declares the capability" is deleted — a platform that serves the capability serves the profiles, and the registry derives that from the platform's own capability identity. The one profile that does not travel is `ConcurrentResolveWarm`, whose measure is a harness instrument rather than a product capability: four persistent OS threads with a per-thread allocation counter. Instruments become a platform declaration of their own (`MeasurementInstrument` and `measurementInstruments`), the registry filters on capability **and** instrument, and the iOS report names the profile it left out together with the reason — `Deferred on this platform: ConcurrentResolveWarm — the harness has no such instrument: four persistent OS threads…` — instead of measuring a sequential loop under an unchanged profile name; its source lives in a Java-family directory compiled into `jvmMain` and `androidMain` alone, so no platform can construct a profile it has no instrument to measure. Deriving the selection also exposed a defect the direct call had hidden: every paragraph scenario inherited `PortableScenario`'s hardcoded `PORTABLE_GLYPHS` route, so the capability the registry derives for it was "none" and a platform that does not declare `END_TO_END_LAYOUT` would have run them anyway — the paragraph half now declares `PARAGRAPH_LAYOUT` through a base class of its own, once. `ThreadAllocationProbe` becomes the allocation instrument's platform declaration the same way — the JVM answers from `com.sun.management.ThreadMXBean`, ART and Kotlin/Native answer null with the reason — which is what lets the concurrent wave's body stay common code. The iOS corpus gains the DejaVu and Amiri faces the paragraph profiles compose with, the Android wrapper gains the eighteen corresponding tests and aligns its no-op guard on "at least one positive counter" (a warm session legitimately publishes its prepared-source bytes as zero), and the corpus both drivers publish is renamed `portable-glyphs-and-paragraph-layout`, because a report must name the corpus it actually measured. Android's benchmark arguments keep the tool's sanctioned refusals and `androidx.benchmark.profiling.mode=none`, and say what neither governs: the runner records a perfetto trace of tens of megabytes for every profile and hands it to the managed device's host-side pull, no argument suppresses that trace without also suppressing the measured files, and the device's own storage fills with it — two runs aborted part-way, at the twenty-fifth profile and at the thirty-second, whenever the pull of one of those traces failed. The measurement therefore deletes the traces the host has already pulled while the run proceeds, and with that the suite reached all forty-two profiles: the tool's own progress line and its results file both report forty-two tests with no failure, no error and no skip, the driver's teardown still reports its `Connection reset` after the last test, and the forty-two counter lines the run published through logcat are unaffected by either. Two harness defects the reports themselves exposed are fixed: the identity task now declares the measured commit as an input, because with no input Gradle kept it up to date across revisions and an APK built after a documentation-only commit published the previous revision's name — the exact failure the publication contract exists to prevent — and the aggregator's Android reader searches for its markers instead of requiring them at the start of a line, because a logcat capture carries the tag prefix while one made with `-v raw` does not, and both record the same measurement. A third defect of the same origin: the figures a report publishes as unavailable were worded by the aggregator's own platform, so an iOS report offered the JVM harness's reasons for the missing allocation instrument — each platform's wording now travels with its own report. The aggregation now refuses a report that measures fewer profiles than the module knows without naming the reason: each platform's coverage is checked against the registry's catalogue and that platform's own published deferrals, so a silently missing profile fails the aggregation instead of printing a dash.
- The non-published `:kalligraphie:bench` module aggregates its three platforms' raw measurement outputs into the publication contract's reports: the opt-in `measurementReport` task joins each platform's tool latency with the scenario metadata and the run's counters, and writes one Markdown per platform plus a comparison, without measuring anything itself. The JVM report reads the newest JMH JSON and its counters JSONL; the iOS report reads the driver's per-iteration samples through the same nearest-rank percentiles the driver used; the Android report reads the logcat-extracted identity and counters and androidx.benchmark's own per-scenario medians and allocation counts, rendered with honest labels — a median stays a median, p95/p99 are published as unavailable rather than invented, and the emulator and debuggable disclosures travel with the identity. A missing input, an unknown scenario or a counter set that consumed nothing fails the aggregation naming the path, because a report assembled from partial runs would look complete while publishing nothing for the absent platform. Two hygiene defects the aggregation itself exposed are fixed: the two cancellation scenarios now publish the maximum observed delay instead of the last reading (which can read zero under the clock's resolution and would be refused as a no-op), and the JVM observations file is truncated before each run so it always holds exactly one measurement run, the same contract the iOS task already kept.
- The non-published `:kalligraphie:bench` module measures the portable glyph scenarios on an Android emulator, completing the second portable platform of the measurement. androidx.benchmark's Gradle plugin targets the classic AGP extensions that AGP 9's KMP device-test DSL does not provide — that DSL has no build-type lever, so the instrumentation APK is debuggable — so the benchmark runs dependency-only: `BenchmarkRule` under `AndroidBenchmarkRunner` in a `withDeviceTest` block with a `mediumPhone` API 35 managed device, one explicit test per scenario selected from the platform's capability identity, the corpus read through the class path the device-test APK packages, and the tool's own `DEBUGGABLE`/`EMULATOR` refusals suppressed through its sanctioned `androidx.benchmark.suppressErrors` argument with the bias disclosed in the identity. The lifecycle maps onto JUnit — untimed `prepare` and `release` around `measureRepeated`, `System.gc()` twice before and after each profile, the operation counter incremented inside the timed block — and the anti-dead-code channel is androidx.benchmark's native `BlackHole`. The measured commit travels to the device as a class-path resource the build writes beside the corpus, because a process on the device cannot call git and the publication contract refuses an unnamed commit. Counters publish through the instrumentation log with a stable marker, captured from the device's logcat buffer during the run — every file-backed channel was measured and rejected, since the test APK is uninstalled after the run and registering extra files with androidx.benchmark's output machinery fails the run's final phase — while the tool's own per-scenario result files (median latency, allocation counts) reach the host through the managed device's additional-output pull, with the per-test method and perfetto traces disabled through `androidx.benchmark.profiling.mode=none` because their tens-of-megabytes pulls repeatedly aborted the run.
- `:kalligraphie:unicode` breaks lines portably: `PortableLineBreakAnalyzer.create()` returns a `BoundedLineBreakAnalyzer` whose UAX #14 opportunities — the boundaries and whether each is optional or source-required — are resolved on every platform from the module's own generated tables instead of the JVM's `BreakIterator`. The rules are the ones UAX #14 publishes for Unicode 16.0, evaluated in their published order, and four new tables join the generated set for the properties the rules read beyond the line-break class: the `Mn`/`Mc` marks that resolve LB1's `SA` class, the `Pi`/`Pf` quotation marks of LB15a, LB15b and LB19, the `Extended_Pictographic`-and-`Cn` scalars that are LB30b's potential emoji base, and the East_Asian_Width `F`/`W`/`H` set UAX #14 spells `$EastAsian`, read by LB19a, LB21a and LB30. The engine's raw decisions are pinned against the whole `LineBreakTest.txt` corpus — 16 672 cases on the JVM — and a JVM cross-check requires the pinned ICU4J reference and the portable engine to publish identical boundaries and kinds over that corpus and real-world multilingual texts; a disagreement is a defect in the portable rules. The behavioral suite calqued on the JVM reference's cases runs on every test target.
- `:kalligraphie:unicode` serves the pinned American-English hyphenation patterns on every platform through `PortablePatternHyphenationService`, which builds the same Liang service the JVM provider builds from a generated Kotlin source instead of a runtime resource: Kotlin/Native has no class path, so `EmbeddedHyphenationPatterns.kt` carries the pattern text, emitted by the new `scripts/unicode/generate_hyphenation_source.py` with the pinned SHA-256 verified at generation time. The vendored `hyph-en-us.pat.txt` resource remains the authority, a JVM cross-check requires both providers to hyphenate the same words identically, and nothing consumes the portable provider yet.
- `:kalligraphie:unicode` ships the complete portable Unicode analyzer: `PortableUnicodeAnalyzer.create()` returns a `BoundedUnicodeAnalyzer` whose grapheme clusters, script-language runs and BiDi runs are all resolved on every platform from the module's own generated Unicode 16.0 tables — the UAX #29 segmenter, the UAX #9 resolver, and the script policy the contract documents, attributing paired punctuation from the same BD16 bracket pairs the BiDi resolution already computed. The language input is parsed and canonicalized by a portable BCP 47 grammar that matches the JVM reference: well-formed tags per RFC 5646 with the case of every subtag normalized and variants sorted among themselves, the grandfathered tags converted to their preferred values, and everything else rejected with the reference's message. The data identity names the generated tables themselves — implementation `Kalligraphie`, version the Unicode release they were generated from. A JVM cross-check runs the pinned ICU4J reference and the portable analyzer over the grapheme and BiDi conformance corpora and real-world multilingual texts and requires identical clusters, scripts and runs, and both grammars must canonicalize and reject the same tags; a disagreement is a defect in the portable rules, the same disposition the HarfBuzz cross-checks take. No capability declares it yet: the analyzer still needs portable line breaking before `UNICODE_ANALYSIS` can honestly turn on.
- The non-published `:kalligraphie:bench` module measures the portable glyph scenarios on the iOS simulator, so the measurement reaches a second platform without waiting for the paragraph capability. kotlinx-benchmark's native backend skips every benchmark target whose Kotlin/Native target differs from the build host, so the simulator is served by a pre-declared fallback instead: the `iosBenchmarkCorpus` task embeds the four fixtures the portable scenarios read as base64 Kotlin source (the mechanism `:kalligraphie:e2e` already uses), a `bench` compilation of the `iosSimulatorArm64` target links the release `glyphBench` executable around the capability-selected scenarios, and the `iosSimulatorArm64Benchmark` task boots an iPhone simulator, spawns the binary through `xcrun simctl spawn --standalone` and captures the report. The protocol mirrors the JVM configuration — three warm-up and five one-second iterations, nanoseconds per operation, nearest-rank percentiles — and the profile refuses a scenario that consumed nothing, exactly as the JVM one does. The identity reports what the simulator process can actually observe (`uname` machine and Darwin kernel, the simulator's iOS version, the Kotlin/Native runtime, and the measured commit the task hands over through the environment), allocation figures stay labelled unavailable with their reason, and the JSONL observations keep the JVM schema plus the per-iteration samples, so one aggregator can read both platforms.
- The non-published `:kalligraphie:bench` module measures the library instead of asserting it. The three former JVM-only opt-in measurements — glyph materialization, incremental paragraph layout and the editable line, including the consumer, session, font-asset handoff and concurrent journeys — become 42 `MeasurementScenario`s whose selection is derived from `:kalligraphie:conformance`'s capability identity, so a platform runs exactly the profiles its declared capabilities can serve and the JVM-only half joins Android and iOS the day `END_TO_END_LAYOUT` lands there. The timed unit, warmup and percentiles come from kotlinx-benchmark (JMH) through a dedicated `jvmBenchmark` compilation, while each scenario keeps publishing the glyphs, lines or operations it actually consumed next to the latency; memory and allocation figures are labelled measured or unavailable, never estimated, and a profile that consumed nothing is refused outright. The same scenario core already compiles for `androidTarget` and `iosSimulatorArm64`, whose harness entries are the next step. The retired `glyphMaterializationMeasurement` and `editableLineMeasurement` tasks, their environment-gated classes and their default test exclusions are gone from `:kalligraphie`; `:kalligraphie:bench:jvmBenchmarkBenchmark` measures all 42 profiles in one opt-in command and writes raw results plus per-scenario counters outside the repository.
- `:kalligraphie:unicode` carries the Unicode Character Database tables a portable analyzer needs, generated from pinned sources by the new `scripts/unicode/` tooling. Nine tables join the hand-committed `UnicodeVerticalOrientation`: the BiDi class and the BD16 bracket pairs, the extended-grapheme break class with `Extended_Pictographic` and the Indic conjunct break, the line-break class, the script with its `Script_Extensions`, and the likely script of a language. All are Unicode 16.0, all searched by hand without allocating, and each states in its KDoc the source file and the SHA-256 it was derived from. `scripts/unicode/ucd.json` pins the URL, the digest and the properties of every payload, `fetch_ucd.py` obtains and verifies them, and `generate_ucd_tables.py --check` proves the committed tables are what those payloads produce — it reproduces `UnicodeVerticalOrientation` byte for byte, which is what fixed the run-table shape and the wrap width. Two shapes of table are emitted and the difference is load-bearing: a **dense** table covers the whole codespace with the source's `@missing` defaults beneath its ranges, while a **sparse** one carries `RANGE_ENDS` so a scalar falling between its ranges answers the property's own default instead of inheriting the range before it. Nothing reads the new tables yet — the analyzer that does, and the capability declaration it enables, are separate work — and they are `internal`, so the module's published surface does not move.
- `scripts/unicode/tests/` covers the acquisition and the generator offline, and the behavioural suite of `:kalligraphie:unicode` pins every table against the Unicode Character Database's own published values: an explicit range, a scalar the `@missing` defaults decide, and a scalar the table omits. As with `scripts/fonts/`, this bookkeeping stays a documented local obligation rather than a CI step.
- `scripts/unicode/PROVENANCE.md` records the exact upstream URL, release, retrieval date and SHA-256 of every payload, with the Unicode License V3 notice the data is distributed under.

- `:kalligraphie:unicode` segments extended grapheme clusters portably, with UAX #29 implemented over the generated tables instead of the JVM's `BreakIterator`. The segmenter keeps exactly the state the boundary rules need — the previous scalar's break class, the length of the run of Regional_Indicators ending at it, whether the text up to it is `Extended_Pictographic Extend*` and whether it ends in the zero-width joiner that follows such a run, and whether it matches `Consonant [Extend Linker]* Linker [Extend Linker]*` — and agrees with the Unicode 16 `GraphemeBreakTest.txt` corpus on every one of its cases. Nothing consumes it yet: it is the segmentation half of the portable analyzer, and it is `internal`.

### Changed
- `:kalligraphie:e2e` runs its behavioural journeys on every target that can compose text instead of the JVM alone. `AdvancedTypographyJourneyTest`, `CffOpenTypeJourneyTest` and their support move from `jvmTest` to a new `src/journeyTest` directory, which `jvmTest`, `androidDeviceTest` and `iosSimulatorArm64Test` compile — the same three targets that verify the composed golden scenes — while the Android host unit test carries none of them, because it runs on a JVM and cannot load the shared library the paragraph facade composes text through. The journeys needed almost nothing to become portable: they already read every byte through the injected `FixtureCorpus`, their two remaining `java.nio.file` imports were unused, and the one real dependency — the JVM-tagged American-English hyphenation provider — is replaced by `PortablePatternHyphenationService.english()`, whose identity, revision, languages and minimums are the same, so the pattern set and the hyphenation output are unchanged. The iOS embedded corpus gains the six fixtures the journeys read and no scene does, the CFF outline oracles included. No expectation was touched and the committed golden manifest is byte-identical: all 45 journey cases pass unmodified on the JVM, on the Android device runtime under ART and on the iOS simulator, which is the first time the paragraph path's own behaviour — justification, hyphenation, fragmentation, incremental reflow, operation bounds — is asserted on a platform other than the JVM.
- **Every platform now declares the complete portable capability surface, and the results are the same on each of them.** Android and iOS move `UNICODE_ANALYSIS` to present through the portable analysis over the generated Unicode 16.0 tables and `END_TO_END_LAYOUT` to present through the paragraph facade built on it, with the profile identifiers `portable-unicode-16.0` and `portable-paragraph`; no capability is absent anywhere, so nothing emits the absence diagnostic. **This is a breaking change for a consumer that tested for the absent branch**: `PortableCapabilityIdentity.presenceOf` now answers `true` and `absenceDiagnostic` returns `null` for both capabilities on Android and iOS. The reasoning behind portable-only is that a device's own Unicode engine varies with its OS release, which would have made `UnicodeDataIdentity` and every golden fingerprint device-dependent. The paragraph facade and the whole facade surface are portable, so `EndToEndLayout` results are byte-identical across platforms — the committed golden manifest is verified unchanged by the JVM on five runner architectures, by the Android unit-test compilation, by the Android device runtime under ART, and by the iOS simulator, composed text included. The Android **host** test compilation is the one place that declares less than its platform: it runs on a JVM and cannot load the shared library the shaping route needs, so it declares the portable Unicode analysis and the portable glyph route and carries the portable scenes alone, while the device runtime carries the full declaration and the whole catalog.
- `EditableLineFacade` and `EditableLineLayoutSession` follow the paragraph and flow facades to `commonMain`, so every text facade of `:kalligraphie` now compiles for every target and the port of the facade surface is complete. The session's `ReentrantLock(true)` and its condition become a new internal `PortableConditionLock` — the JVM and Android actuals are the same fair lock and condition, the Apple actual is the platform's own `NSCondition` — and its `ThreadLocal` operation depth becomes a per-thread count keyed by a portable thread token, the calling thread's own object on the JVM and its pthread identifier on Apple. Two details are worth a consumer's attention and neither changes behaviour: the lock is documented as non-reentrant, which the JVM and Android actuals enforce through the lock's own hold count while the Apple one could only deadlock, so a future nesting cannot pass on one platform and hang on another silently; and the count is taken inside the lock rather than in thread-local storage, which is what the session's own `close` and `layout` already assume. `EditableLineLayoutSession.close`'s decision moves from the body of an inline `withLock` into a private function that returns it, because the portable lock is not inline and a non-local return is no longer available. The published results, the concurrency contract, and the reentrant-close rejection are unchanged.
- The paragraph and flow text facades of `:kalligraphie` — `EditableParagraphFacade`, `IncrementalParagraphLayoutSession` and `FlowCompositionFacade` — move from `jvmMain` to `commonMain`, so the paragraph and flow paths compile for every target. Their analysis is now the portable one: they call `PortableUnicodeAnalyzer` and `PortableLineBreakAnalyzer`, whose results the JVM cross-checks already pin against the ICU-backed reference, and the paragraph facade canonicalizes its language through `PortableUnicodeAnalyzer.canonicalizeLanguageTag` instead of the JVM factory's. `@Synchronized` becomes an internal portable lock whose JVM and Android actuals are the object monitor (identical semantics) and whose iOS actual is `atomicfu`'s reentrant lock; `Collections.unmodifiableList` becomes the api module's public `immutableListSnapshot`. The analysis the facades publish is unchanged, golden fingerprints included. One consequence for consumers: `IncrementalParagraphLayoutSession.open` loses the `@JvmOverloads`-generated Java overloads, so Java callers must pass every parameter explicitly, while Kotlin callers keep their defaults. `EditableLineFacade` and `EditableLineLayoutSession` stay on the JVM for now: their session waits on a condition variable and tracks per-thread reentrancy, which is the next piece of portable concurrency.
- `:kalligraphie:unicode` resolves the bidirectional embedding levels portably, with UAX #9 implemented over its own generated tables instead of ICU's `Bidi`: the explicit embedding structure and the isolating run sequences (X1–X10) with their sos and eos types, the weak rules W1–W7, the bracket pairs with their N0 resolution, the neutral rules N1–N2, and the implicit levels I1–I2. The machinery around the core — the FSI directions of P2 and P3, the bracket pairs of BD16, and the normative repair of the X9-removed characters — is shared with the ICU-backed JVM path, so the two implementations cannot drift. The resolver agrees with the Unicode 16 `BidiTest.txt` and `BidiCharacterTest.txt` corpora on every case, on the JVM and on the Android device runtime, and a shared boundary-level distinction the corpora forced makes the sos and eos of a sequence read the embedding a character sits in rather than the level X8 assigns the separators for their own resolution. - macOS system faces that publish their family and style names only as Macintosh Roman `name` records are no longer rejected whole as `name table is invalid`. On a stock macOS 27.0.1 install, 172 of 786 `/System/Library/Fonts` faces across 56 files — Menlo, Helvetica, Helvetica Neue, Times, Courier, Monaco, Geneva, Symbol, ZapfDingbats and Apple Color Emoji among them — carry no Unicode name record at all and were unreachable to every capture route. `SfntReader` now decodes platform 1 / encoding 0 records as a last resort after every Unicode record, with the full Macintosh Roman high-byte mapping, `languageId == 0` preferred over other Macintosh languages, and Unicode names still winning whenever both encodings are present.
- The paragraph ellipsis marker is measured with the font instance actually retained at the candidate anchor instead of the first available instance, and the final marker width is revalidated before publication. With per-span instances a boundary could be chosen against one face or variation and published with another, so a truncation that fitted with a narrow marker could emit a marker too wide for the run it was placed in.
- The `:kalligraphie:e2e` harness is byte-stable on a Windows checkout. `.gitattributes` pins text files to LF everywhere, because the harness digests committed resources — the hyphenation pattern it verifies by SHA-256, the golden manifest, the claims export — and compares the generated pages byte for byte, all of which a `core.autocrlf` checkout rewrote and broke. The claims export no longer proves itself by handing the document to a host `python3`: a unit test that spawned an interpreter, discovered its name and pinned its encoding was asserting the harness's own plumbing more than the export's value, and it is what failed on the Windows runner. What the export must guarantee — its hand-written escaping survives a hostile reason — belongs with the tool that consumes it.
- The PGM/PPM inspection dumps of `:kalligraphie:e2e` open upright, whichever route produced them. `GoldenImage` now declares the row order of its canonical bytes — `GoldenOrientation.IMAGE` (row zero at the visual top) or `GoldenOrientation.DESIGN` (row zero at the visual bottom, the order the CPU rasterizer returns for a y-up outline) — and the five scenes that hand the rasterizer's own rows to the model declare `DESIGN`: the two CFF capitals, the TrueType capital, the VVAR metrics capital and the COLR v0 paint. `GoldenImageReframer` carries that declaration through an auto-sized frame instead of silently rebuilding its content as image-oriented, and `GoldenDumpWriter` reverses a design-oriented raster exactly once, before compositing RGBA over white, so the same shape reads the same way in every dump. The composed canvases and the normalized bitmap strikes already produce image orientation and are written unchanged, and the reversal is a no-op for them. The golden fingerprints, the committed manifest, the ratchet and the in-repo scene frames are untouched: the change is in the inspection artifact and in the model's declaration, not in the bytes the digests cover.
- Instanced glyph ink bounds on the portable TrueType metric route. `:kalligraphie:font:scaler`'s `PreparedTrueTypeFont.readGlyphMetrics` now feeds `GlyphMetrics.bounds`/`scaledBounds` from the requested glyph's **instanced** outline bbox — the varied `gvar` outline points (phantom points excluded, exactly as the static `glyf` header excludes them), computed through the existing `GlyfReader` bounds and passed to the bounds-taking `MetricsReader` overload — instead of the static, non-varied `glyf` header bbox. The value is memoized per `(glyphId, ordered normalized location)` by a bounded, common-safe copy-on-write cache on the shared per-face decoder, so the paragraph projection path amortizes repeated glyphs; the default instance still reads the static header and the CFF/CFF2 route is unchanged. Because the non-default path now materializes the outline under `metricsOutlineProfile()`, a glyph whose `glyf` header is readable but whose outline exceeds the profile (or is malformed) now fails that `metrics()` call, where the `HVAR`-present path previously succeeded without decoding the outline. The audited `NotoSansJP-VerticalFixture.ttf` glyph `A` = gid 1 now reports `(11, 0, 563, 726)` at the default, `(0, 0, 622, 737)` at `wght = 500` and `(-8, 0, 668, 745)` at `wght = 900`; the CFF2 route is a regression-guarded no-op. The memo is capped at 512 `(glyphId, ordered normalized location)` pairs per face with insertion-ordered eviction, so the retained bounds stay bounded. Because the metric route asks for the bounds on every non-default read, an advance-only `metrics()` caller also pays one outline decode per unique `(glyphId, location)` pair on a cache miss, amortized by the memo across repeated glyphs at one location but not free for the first read of each pair. Known residual gap: un-cross-checked instanced **composite** bounds may differ from HarfBuzz for rotated or skewed components (the engine unions the transformed child *points*; HarfBuzz unions component *bboxes*/instructions), and a header-bearing glyph with zero contours keeps the static header bbox while HarfBuzz may return empty extents; both are deferred with the ink-bounds cross-check. This makes the engine value correct; the ink **bounds** are now cross-checked against HarfBuzz through the republished binding's `hb_font_get_glyph_extents` (see the ink-bounds cross-check entry below), on non-composite glyphs. Instanced composite ink bounds remain un-cross-checked: the audited glyph is simple, and the only composite ink-bounds evidence is scaler-level.
- Corrected the OpenType variation-region axis rule for `gvar` (`cvar`) tuple variation stores so it matches the `ItemVariationStore` and the specification. `:kalligraphie:font:sfnt` extracts one shared internal `VariationRegionAxisFactor`, makes both `TupleVariationScalars.scalar` (the `gvar` route) and `VariationStoreEvaluator` delegate to it, and derives the peak-only tent from `start = min(peak, 0.0)` and `end = max(peak, 0.0)` instead of a second branch. A tuple region that spans zero or whose bounds are mis-ordered now ignores that axis (`1.0`, the OpenType "Algorithm for Interpolation of Instance Values" / fontTools `supportScalar(..., ot = true)` rule) instead of interpolating through zero or returning `0.0`, so an affected simple-glyph outline delta (and its IUP-propagated points), composite component offset and phantom-point delta (hence derived advance and side-bearing variation) is no longer halved or silently dropped. This is the deliberate renderer policy: fontTools' partial `varLib.instancer` drops such tents while the render-time (`ttGlyphSet`) and whole-font (`varLib.mutator`) paths and the specification apply the fallback, and this engine is a renderer. Peak-only and well-formed-region behaviour is unchanged, and no public signature changed.
- SVG paint and clip paths report `ResourceLimitExceeded` when supported geometry exceeds declared contour, point or byte limits, preserving the distinction from unsupported paint capabilities.
- Default snapshot publication version when no workflow version is provided.
